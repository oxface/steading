# Stack Decisions

Living decision record. Last direction update: **August 22, 2026**. The status words are intentional:

- **Confirmed** — use it unless the documented revisit trigger occurs.
- **Conditional** — do not install it until its need appears.
- **Provisional** — benchmark or spike it before committing.
- **Deferred** — a credible option whose trigger has not occurred.
- **Replaced** — an earlier selection changed after this audit.

The goal is not maximum novelty. Seneschal is the product; Steading is its small, understandable reference cluster. Prefer portable contracts and replaceable boundaries, but do not manufacture comparisons when the current choice is working.

## Frontend

- **Confirmed — React + TypeScript + Vite, as an SPA.** This keeps the browser boundary visible and avoids framework-specific server semantics. Vite's default production target is modern browsers; that matches this personal app, but a public product would need an explicit browser support policy and possibly `@vitejs/plugin-legacy`. [Vite build targets](https://vite.dev/guide/build)
- **Confirmed — Tailwind CSS v4.** It is a good learning target for modern CSS, but its floor is modern Chrome/Safari/Firefox and it is intentionally incompatible with Sass/Less/Stylus. Those are accepted constraints here. [Tailwind compatibility](https://tailwindcss.com/docs/compatibility)
- **Confirmed — shadcn/ui, using the current Base UI default for new components.** shadcn distributes source into this repo rather than hiding it behind a package, which is ideal for learning and customization. The cost is that we own the copied code and upstream improvements are not automatic. Existing Radix examples remain useful, but do not mix primitives casually. [shadcn documentation](https://ui.shadcn.com/docs) · [Base UI default change](https://ui.shadcn.com/docs/changelog)
- **Confirmed — TanStack Router with file-based routing.** Typed path/search state is valuable and the route tree stays portable within React. Its generated route tree must be excluded from formatting/linting; type inference and IDE performance are revisit triggers if the route graph becomes large. [File-based routing](https://tanstack.com/router/latest/docs/routing/file-based-routing) · [type-safety guidance](https://tanstack.com/router/latest/docs/guide/type-safety)
- **Confirmed — TanStack Query for server state.** Its defaults are deliberately active: cached data is stale immediately, stale queries refetch on mount/focus/reconnect, and failures retry. Every query exercise must choose `staleTime` deliberately so this behavior is learned rather than mistaken for random traffic. [Important defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)
- **Conditional — Zustand.** Local state, lifted state, Context, and `useReducer` come first. Add Zustand only when genuine cross-tree client state appears; never mirror Query data into it. This removes an unnecessary day-one dependency without rejecting the tool.
- **Confirmed — React Compiler, with ESLint diagnostics and profiling.** The compiler is stable, but it does not make render-model knowledge optional and it depends on correct Rules of React. Profile at least one screen and treat compiler lint failures as correctness feedback. [React Compiler introduction](https://react.dev/learn/react-compiler/introduction)
- **Confirmed — ESLint + Prettier + `prettier-plugin-tailwindcss`.** ESLint retains the mature React hooks/compiler rule ecosystem. Biome and oxlint are possible later consolidation experiments, not useful complexity at this repository size.
- **Confirmed — pnpm for repository orchestration and the Seneschal web app; npm for the Aspire AppHost.** Strict pnpm dependency resolution remains useful for product code. The TypeScript AppHost is an isolated tooling package using npm because Aspire 13.5 invokes pnpm with `--ignore-workspace`, which bypasses pnpm 11's project build-script allowlist and prevents `esbuild` from installing. Revisit the npm exception when Aspire and pnpm support a project-scoped, reproducible build approval through that invocation. Pin both package managers and the Node major before CI so local and CI installs do not drift.
- **Confirmed — Vitest + React Testing Library when behavior appears; Playwright at the first deployed user journey.** Playwright is no longer postponed indefinitely: the first FE→API flow is its trigger. Select a form library only at the first non-trivial form; native forms plus schema validation remain the baseline.
- **Deferred — TanStack Start.** Reconsider only for SSR or a TypeScript BFF. **Next.js remains rejected** because it adds a server/component deployment model the project is not trying to learn.

## Backend and data

- **Confirmed — Python 3.14 for Seneschal.** The user is much more experienced in .NET, but Python is intentional here: the product's main learning target is the Python agent ecosystem, and LangGraph's Python surface gives the shortest path from ideas to experiments. This is a product-scoped choice, not a claim that Python is generally superior to .NET. If Python ecosystem friction stops product progress, that is the revisit trigger.
- **Confirmed — FastAPI + Pydantic.** They make HTTP contracts and validation explicit without imposing a full application architecture. Async handlers must not call blocking libraries, and Kubernetes should normally scale one worker per pod rather than hide multiple workers inside a pod. [FastAPI async guidance](https://fastapi.tiangolo.com/async/) · [deployment concepts](https://fastapi.tiangolo.com/deployment/concepts/)
- **Confirmed — SQLAlchemy 2 async + psycopg 3.** This is intentionally more explicit than SQLModel. The important trap is concurrency: an `AsyncSession` is not shareable across concurrent tasks, and operations on one psycopg connection serialize. Use one session per request/task and let SQLAlchemy own pooling; do not layer `psycopg_pool` underneath without a measured reason. Direct psycopg async on Windows also requires a compatible event loop, while deployed code runs on Linux. [SQLAlchemy session model](https://docs.sqlalchemy.org/en/20/orm/session_basics.html) · [psycopg async behavior](https://www.psycopg.org/psycopg3/docs/advanced/async.html)
- **Confirmed — PostgreSQL, with Alembic from the first real table.** It is the system of record, not a universal queue, cache, or log store.
- **Conditional — pgvector.** Install it when retrieval has a measured need. Start with exact search; HNSW spends more memory and build time for speed, and approximate indexes trade recall for performance—especially with filters. Measure recall against exact results before choosing an index. [pgvector indexing](https://github.com/pgvector/pgvector#hnsw)
- **Confirmed — uv + ruff + pyright strict + pytest/httpx.** uv owns Python project/lock/environment operations, ruff owns lint/format, and pyright remains the type gate. `ty` is a watch item, not a second checker. [uv project migration model](https://docs.astral.sh/uv/guides/migration/pip-to-project/)
- **Confirmed — signed httpOnly cookie sessions for one backend.** Move to server-side Postgres sessions when revocation, session size, or multi-instance behavior requires it. Add an external IdP only when multiple apps need shared identity.
- **Confirmed — Lefthook for local cross-language formatting gates.** It is a small, language-neutral binary and can run independent hooks in parallel. CI must run the same checks independently because Git hooks are bypassable. [Lefthook](https://github.com/evilmartians/lefthook)
- **Deferred — .NET service.** .NET remains the user's production anchor and is the preferred language for a future integration when a real boundary benefits from it. Do not add a token C# service merely for polyglot architecture or CV value.

## Agent runtime and durable execution

- **Confirmed — raw provider calls before framework helpers.** Tool calling, streaming, and structured output are implemented once from primitives before their framework equivalent.
- **Confirmed — LangGraph 1.x for the stateful agent graph.** It directly teaches graph state, interrupts, checkpointing, and resumability and can be used without the broad `langchain` package. Its central weakness is upgrade compatibility: a resumed checkpoint executes the current graph code, so graph/state schema migrations are an application responsibility. Pin versions and add resume-old-checkpoint tests before upgrades. [LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview) · [backward compatibility](https://docs.langchain.com/oss/python/langgraph/backward-compatibility)
- **Confirmed — PostgresSaver for agent checkpoints.** It provides graph durability and human-in-the-loop state, not a general task queue or exactly-once side-effect system. [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- **Conditional — DBOS for non-agent business workflows.** Do not wrap LangGraph pre-emptively. Adopt DBOS when the product has a durable multi-step workflow, queue, schedule, or exactly-once database transaction that LangGraph should not own. DBOS is MIT and Postgres-backed, but production operations introduce its Conductor/control-plane and connection-management concerns. [DBOS architecture](https://docs.dbos.dev/architecture) · [workflow semantics](https://docs.dbos.dev/python/tutorials/workflow-tutorial)
- **Alternatives kept explicit:** Restate has a strong dedicated durable-runtime model but adds a server and uses BSL 1.1; Hatchet is MIT and task-queue-shaped but adds more infrastructure; Dapr Workflow is the preferred revisit if first-class Python/.NET parity becomes mandatory. Temporal and Azure Durable Functions remain outside scope.
- **No framework comparison milestone.** LangGraph is selected because learning explicit graph state and multi-step investigations is a primary goal. PydanticAI and vendor agent SDKs remain alternatives, not mandatory spikes. Revisit only if LangGraph creates a concrete product limitation.

## Models and inference

- **Confirmed — Ollama on the Windows host for the initial local provider.** It keeps the physical GPU outside the VM and gives OpenWebUI and Seneschal one reachable local endpoint. Its OpenAI-compatible API is not the full OpenAI API, so the adapter must test required capabilities rather than infer them from the base URL. [Ollama OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility)
- **Confirmed — capability-based provider adapters.** Ollama is first. A direct OpenAI or Azure OpenAI adapter can be added when hosted-model quality is useful; a managed Foundry agent is not the initial architecture. Domain code must not depend on provider-specific response objects.
- **Provisional — Qwen3.5 9B through Pi for bounded local coding assistance.** On the current 16 GB GPU it remains fully GPU-resident at the tested 64K and 128K Ollama context allocations and is fast enough for experiments. Its repository analysis still produced material factual errors, so it is an optional executor for small, already-specified tasks with objective checks, never the source of architecture, requirements, or final review. DeepSeek Harness remains another developer harness, not a replacement for LangGraph. See [the local evaluation](local-coding-agent-evaluation.md).
- **Confirmed — coding-harness context metadata must match the inference server.** Ollama's allocated context is the real per-request ceiling. Harness counters may advertise a different configured maximum, and cumulative input totals sum repeated turns/tool calls rather than representing one prompt. The tested Pi profile should advertise 128K while Ollama is allocated 128K; larger values require a new fit and latency check.
- **Confirmed — app context is selected by eval, not by the coding profile.** Seneschal's bounded typed investigations should start by testing a 16K–32K budget. A 128K coding context is not an app requirement, and a model's advertised maximum is not evidence that the quality or hardware fit is useful at that size.
- **Deferred — additional local inference hardware.** The existing RTX 4080 Super is enough for the experiment. A second machine with an RTX 3060 would provide a separate serving endpoint, not pooled network VRAM; another GPU helps only when a model is sharded inside one host and does not accelerate a model already fully resident on the primary GPU. Revisit after a measured concurrency, availability, or larger-model requirement.
- **Deferred — in-cluster model serving.** vLLM is a high-throughput inference server, not an agent orchestrator; OpenHands is an agent application, not a replacement for Ollama. Neither solves the current need. Revisit vLLM or another server only when there is cluster-attached GPU hardware or measured throughput/serving requirements. Do not plan GPU passthrough into the current Hyper-V VM.
- **Confirmed — separate internal MCP boundary for cluster reads.** `seneschal-api` is the MCP client and has no cluster credentials. `seneschal-tools` owns typed Kubernetes/Flux/observability adapters with a read-only identity, validation, redaction, audit, and output limits. Ordinary in-process functions remain appropriate for private application logic.
- **Deferred — action MCP server.** If write operations become useful, implement them in a separate deployment and identity with narrow RBAC, explicit approvals, idempotency, and audit. Never broaden the read server in place.

## Local platform and Kubernetes

- **Confirmed — single Ubuntu VM on a dedicated Hyper-V internal/NAT network with k3s as the local cluster.** This matches the preferred on-demand start/stop workflow and isolates cluster state from the main Windows environment. The `Steading` switch uses `192.168.50.0/24`: Windows is the NAT gateway and Ollama host at `192.168.50.1`, while the VM and k3s node are pinned to `192.168.50.10`. Local hosts-file entries provide `steading-cluster.steading.test` and application names. The initial Default Switch design was replaced after a Windows restart changed its DHCP subnet while Hyper-V resumed the VM from saved state; k3s retained the previous advertised address, leaving the Kubernetes API Service endpoint stale and crashing every Flux controller. Keep the unrestricted k3s kubeconfig root-only on the VM; use key-only SSH for bootstrap and break-glass administration, configure Hyper-V to shut the guest down rather than save it, and use Git as the routine write path after Flux bootstrap. WSL remains an optional developer shell, not the cluster host. Talos remains a credible future appliance-style node OS, but k3s on Ubuntu keeps the first cluster smaller and more inspectable. This is not HA and does not pretend to test real failure domains. [k3s requirements](https://docs.k3s.io/installation/requirements) · [Hyper-V NAT networking](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/setup-nat-network) · [k3s cluster access](https://docs.k3s.io/cluster-access) · [Flux bootstrap](https://fluxcd.io/flux/installation/bootstrap/github/)
- **Deferred — Proxmox VE.** Proxmox becomes sensible on a separate physical host when VM lifecycle, templates, backups, networking, or multi-node experiments are themselves goals. Nested Proxmox on the current Hyper-V setup adds layers without improving the Seneschal path. On rented Hetzner VMs, use the provider's VMs directly and install k3s; do not add Proxmox unless renting suitable dedicated hardware and intentionally building a virtualization layer. [Proxmox installation model](https://www.proxmox.com/en/products/proxmox-virtual-environment/get-started) · [hardware requirements](https://proxmox.com/en/products/proxmox-virtual-environment/requirements)
- **Confirmed — OCI images and Compose for pre-cluster development.** Docker is the default implementation because of ecosystem fluency, but manifests and images must not rely on Docker-only runtime behavior; Podman remains a viable local replacement.
- **Confirmed — Gateway API as the portable traffic contract.** The API is the skill; the controller is replaceable. [Gateway API implementations](https://gateway-api.sigs.k8s.io/implementations/)
- **Confirmed — k3s-bundled Traefik v3.** Enable its Gateway API support and learn the portable Gateway/HTTPRoute resources. Do not add Envoy just for assumed AKS parity: AKS ingress/data-plane choices are configuration-specific and can be decided from the actual target later. Migration is mainly controller-specific configuration, not an application rewrite, when the Gateway API contract is kept clean. [k3s networking services](https://docs.k3s.io/networking/networking-services)
- **Confirmed — Kustomize for owned manifests; Helm through Flux for third-party charts.** Avoid templating owned YAML prematurely and avoid direct Helm releases that GitOps cannot reconcile.

## GitOps, secrets, and delivery

- **Confirmed — upstream Flux controllers and CLI as the first cluster delivery path.** Flux becomes authoritative immediately after the k3s and controller bootstrap, before application workloads accumulate. Kubernetes learning reps use hand-authored manifests, local rendering, Flux reconciliation, and status/debugging rather than a temporary manual-apply workflow. The model keeps reconciliation visible through Kubernetes resources and transfers to Azure's Flux extension. Learn the CLI and CRDs first. Flux has no project-maintained UI, so select an ecosystem UI only after operating Flux and identifying which views are actually missing; Seneschal's integration catalogue can link to it. Argo CD is not a mandatory comparison spike. [Flux bootstrap](https://fluxcd.io/flux/cmd/flux_bootstrap/) · [Azure Flux v2 model](https://learn.microsoft.com/en-us/azure/azure-arc/kubernetes/conceptual-gitops-flux2) · [Flux UI FAQ](https://fluxcd.io/flux/faq/#does-flux-have-a-ui--gui)
- **Replaced — plaintext Secrets in Git → SOPS + age from the first GitOps secret.** Base64 is not encryption. Flux supports native SOPS decryption and recommends age over OpenPGP; the age private key must be backed up outside Git or a rebuilt cluster cannot decrypt anything. [Flux SOPS guide](https://fluxcd.io/flux/guides/mozilla-sops/)
- **Conditional — External Secrets Operator.** Start with SOPS because no external secret store is needed for the thin cluster. Add ESO when Azure Key Vault becomes the source of truth; applications continue consuming Kubernetes Secrets or injected environment/file values instead of calling Key Vault directly. OpenBao is a viable local/self-hosted source with published container images and an optional UI, but operating it is additional security-critical infrastructure, so use it only for an intentional secrets-management exercise. [ESO architecture](https://external-secrets.io/latest/introduction/overview/) · [Azure Key Vault provider](https://external-secrets.io/latest/provider/azure-key-vault/) · [OpenBao installation](https://openbao.org/docs/install/) · [OpenBao UI](https://openbao.org/docs/configuration/ui/)
- **Confirmed — GitHub Actions + GHCR.** CI builds/tests/scans; Flux deploys. Workflows pin actions by immutable commit before the repository handles meaningful credentials.
- **Deferred — infrastructure as code.** Kustomize and Flux own cluster workloads; Hyper-V can be configured manually for the first VM. When there is a real repeatable infrastructure graph—AKS resources or a dedicated Proxmox host—start with OpenTofu for an open Terraform-compatible workflow. Terraform remains the obvious CV-recognition alternative, and Pulumi is appropriate if C#/Python abstractions genuinely simplify the graph. Choose from the actual provider/resource requirements, not a comparison exercise. [OpenTofu state encryption](https://opentofu.org/docs/language/state/encryption/) · [Pulumi state backends](https://www.pulumi.com/docs/reference/state/)

## Observability

- **Confirmed — OpenTelemetry APIs/SDKs plus the upstream Collector.** OTLP is the portable boundary. Start with one Collector gateway deployment; add agents/DaemonSets only when node-level collection needs them. [Collector deployment patterns](https://opentelemetry.io/docs/collector/deploy/) · [gateway pattern](https://opentelemetry.io/docs/collector/deploy/gateway/)
- **Confirmed — single-node VictoriaMetrics + VictoriaLogs + Grafana + Tempo for the homelab.** Single-node deployments fit the resource constraint and PromQL knowledge transfers through MetricsQL. The costs are a less common LogsQL query language, a smaller ecosystem than Prometheus/Loki, and four separately operated products. Loki can also run monolithically, but its durable path centers on object storage and its label model discourages high-cardinality fields such as trace IDs. Revisit with measured CPU/RAM/disk and query usability after the observability stage, not vendor benchmarks alone. [VictoriaMetrics single-node guidance](https://docs.victoriametrics.com/victoriametrics/single-server-victoriametrics/) · [VictoriaLogs/Loki comparison](https://docs.victoriametrics.com/victorialogs/faq/#what-is-the-difference-between-victorialogs-and-grafana-loki) · [Loki architecture](https://grafana.com/docs/loki/latest/get-started/architecture/)
- **Sequencing confirmed.** The thin cluster and first OpenWebUI workload come before the full stack. The first read-only Seneschal stage uses Kubernetes and Flux state; the next stage adds the observability stack and its MCP adapters. Health checks, structured logs, and basic agent traces still begin when each service appears.

## Revisit triggers, not comparison milestones

- **Flux UI:** after CLI use reveals missing operational views; evaluate the current ecosystem then.
- **Envoy/Cilium/alternate Gateway implementation:** when an actual AKS target or networking requirement is known.
- **OpenBao/ESO:** when secrets need an external source of truth or a secrets-operations exercise is explicitly chosen.
- **OpenTofu/Terraform/Pulumi:** when there is a real repeatable infrastructure graph.
- **Proxmox:** after acquiring a dedicated host or choosing virtualization operations as a goal.
- **vLLM or another in-cluster server:** when cluster-attached GPU hardware or measured serving demand exists.
- **Alternate agent framework:** when LangGraph causes a demonstrated product or operability problem.
- **Frontend/tooling watchlist:** Biome/oxlint, ty, TanStack Start, eBPF/OBI, and Granian require a measured current-stack limitation, not trend interest.
